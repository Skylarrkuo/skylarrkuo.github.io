双人份 · Deux：把“今天吃什么”变成两个人的日常仪式

两个人，一日三餐，很多很多年。

项目仓库

源码已开源在 GitHub：Skylarrkuo/family-meal-order。

一、不是外卖平台，而是一张只属于两个人的餐桌

“今天吃什么？”看起来是一个很小的问题，却经常变成一天里最难回答的问题之一。一个人的时候可以随便解决，两个人一起生活之后，早餐、午餐和晚餐都多了一层协作：谁想吃什么、家里还缺什么、上次吃过的菜能不能再来一次、这顿饭两个人是不是都确认了？

双人份 · Deux 就是为这个场景做的一个私人点餐与吃饭记录应用。它不试图成为一个面向陌生用户的复杂平台，而是把功能收拢到一个很具体的目标上：让两个人更轻松地安排每天的饭，也把一起吃过的饭留下来。

二、从一顿饭开始，串起完整的生活记录

登录后，首页是一张“餐桌”视图。用户可以切换日期，分别安排早餐、午餐和晚餐；每个餐次下展示两个人各自的点餐心愿，同时自动汇总需要准备的菜品和数量。

flowchart LR
    A[选择日期] --> B[选择餐次]
    B --> C[添加预设菜单]
    B --> D[输入临时菜品]
    C --> E[形成个人心愿]
    D --> E
    E --> F[合并菜品与数量]
    F --> G[两个人分别确认]
    G --> H[按餐次聚合通知]

这种设计有一个很实用的细节：同一个餐次的菜品会合并数量。例如两个人都点了番茄炒蛋，餐桌上不会出现两条互相重复的准备清单，而是直接显示“番茄炒蛋 ×2”。菜单被改名或下架后，历史订单仍然保留当时的菜名快照，过去的记录不会因为今天的菜单变化而失真。

除了直接点餐，应用还提供一个轻量的随机推荐：它会偏向两个人共同收藏的菜，也会参考最近 14 天的记录，尽量避免连续重复。推荐不是为了制造复杂的算法体验，而是为了在两个人都不想动脑时，给餐桌一个可以接受的答案。

三、两个人的“共同确认”比单方面提交更重要

普通订单系统往往只有“提交”这一种状态，但共同生活里的饭菜安排并不总是单方面决定。Deux 为每个餐次保留两个人各自的确认状态：一方点头之后，餐桌会显示等待另一方确认；两个人都确认后，这顿饭才变成“说定了”。

收藏也采用同样的双人视角：每个人可以维护自己的喜欢，只有两个人都收藏的菜才会进入“共同喜欢”。这让推荐、菜单管理和真实偏好之间形成了一个自然闭环。

四、历史、照片与月报：让点餐不止停留在今天

餐桌之外，项目还把“吃过什么”整理成了三种回看方式：

  1. 历史：按月份和成员筛选过去的订单，并支持把某一顿饭快速复刻到新日期。
  2. 回忆：上传 JPG、PNG 或 WebP 照片，配上一句当时的话。
  3. 月报：把当月一起吃饭的天数、点餐次数、照片数量、共同喜欢和常吃菜品汇总成一张回忆卡片。
flowchart TD
    A[每天点餐] --> B[订单与菜品快照]
    A --> C[上传用餐照片]
    B --> D[历史复刻]
    B --> E[月度统计]
    C --> E
    E --> F[月报回忆卡片]

它们共同完成了一个从“计划”到“记忆”的闭环：今天先决定吃什么，吃完之后留下照片，月底再回头看看这个月一起好好吃了多少顿饭。

五、技术实现：Flask API + Vue 3 + SQLite

项目采用前后端相对清晰的分工。Flask 负责登录、API、数据库、文件访问和静态资源服务；Vue 3 负责餐桌、历史、喜欢、回忆、月报和设置等页面；SQLite 用来保存成员、菜单、订单、收藏、确认、照片回忆和寄语等数据。

flowchart LR
    A[Vue 3 页面与组件] -->|Vite build| B[带哈希静态资源]
    B --> C[Flask 模板与静态目录]
    C --> D[Flask / Gunicorn]
    D --> E[(SQLite)]
    D --> F[私有照片目录]
    D --> G[微信公众号模板消息]

生产构建采用 Vite 输出前端静态资源，再由脚本根据 manifest 生成 Flask 模板。因此线上只需要运行 Python 服务，不需要把 Vite 开发服务器暴露出去。Dockerfile 使用多阶段构建：前一阶段编译 Vue，后一阶段只保留运行 Flask/Gunicorn 所需的内容。

六、从网页到手机：PWA、TWA 与原生客户端

这个项目并没有把移动端当成最后再补的适配层。当前仓库同时提供三条移动端路径：

  • PWA：提供 Manifest、Service Worker、离线提示页和应用图标。
  • TWA：通过 Android Trusted Web Activity 将已经部署的 HTTPS 网站包装成 APK。
  • 原生 Android：mobile-native/ 提供 Kotlin + Jetpack Compose 工程，逐步迁移登录、点餐、推荐、收藏、确认、通知、历史、月报、照片和设置。
flowchart TD
    A[同一套 Flask API] --> B[Vue Web]
    A --> C[PWA / TWA]
    A --> D[Kotlin + Compose 原生客户端]
    B --> E[浏览器使用]
    C --> F[可安装的 Android 体验]
    D --> G[原生 Debug / Release App]

TWA 和原生客户端都依赖真实部署环境的 HTTPS、包名和签名配置；这些配置与具体域名和 release keystore 绑定，不能直接套用示例值。

七、私人应用也要认真做安全边界

Deux 的定位是“两个人共用的私人应用”，因此采用共享密码登录，而不是多租户账号体系。这个定位需要在部署时保持清醒：它适合家庭、伴侣或小范围私人使用，不适合作为允许陌生用户自由注册的公开平台。

项目已经覆盖了几类基础防护：

  • 登录会话使用 HttpOnly、SameSite Cookie。
  • 所有写操作进行 CSRF 校验。
  • 后端校验成员、日期、餐次、菜品、数量和文本长度。
  • 上传照片限制为 8 MB，并检查扩展名和文件内容特征。
  • 照片通过登录保护路由访问，不直接暴露上传目录。
  • Docker 使用命名卷持久化 SQLite 数据库和照片目录。

如果要放到公网，仍然建议在 Flask/Gunicorn 前增加 Nginx 或 Caddy 等 HTTPS 反向代理，并在确认 HTTPS 生效后开启 SESSION_COOKIE_SECURE=true。同时需要定期备份数据库和照片；升级前尤其要注意不要误用 docker compose down -v，因为它会删除保存数据的命名卷。

九、结语：把系统做小，把日子过具体

双人份 · Deux 最有意思的地方，不是它包含了多少页面，而是它把一个很小的生活问题持续做深：两个人今天吃什么，以及以后还能不能想起一起吃过什么。

从点餐到确认，从准备清单到微信通知，从一顿饭到一张月报卡片，应用把原本散落在聊天记录、备忘录和相册里的内容，收拢成了一张有记忆的餐桌。

对个人项目来说，这也是一个很好的方向：不必一开始就服务所有人，先把一个具体关系里的高频问题解决好。功能可以很小，但只要它真的让每天的生活轻松了一点，就已经足够值得被做出来。
